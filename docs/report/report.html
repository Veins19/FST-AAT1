2. PROBLEM STATEMENT AND OBJECTIVES

2.1 Problem Statement

Students and working professionals handle many assignments, project milestones and personal commitments at the same time, each with a different priority and deadline. Tracking these in paper lists, chat messages or scattered notes makes it hard to see what is still pending, which items are overdue and what has already been completed. Existing task tools are often heavy, account-based or cluttered with features that a single user does not need. Therefore, there is a need for a lightweight, self-hosted full-stack TaskFlow application that stores tasks centrally behind a validated REST API and presents them through a clean, responsive browser interface with instant filtering, search and progress statistics.

2.2 Project Objectives

  • RESTful Backend Service: To design and implement an Express.js API (/api/tasks, /api/stats) supporting create, read, update and delete operations with correct HTTP status codes (201, 204, 400, 404).
  • Responsive Frontend Client: To build a single-page interface in HTML, CSS and vanilla JavaScript that consumes the API using the Fetch API and re-renders after every change.
  • Server-Side Validation & Safe Rendering: To validate titles, priorities and due dates on the server and to HTML-escape user text so that stored content cannot inject scripts (XSS).
  • Productivity Features: To provide priority badges, due dates with overdue highlighting, All / Active / Done filtering, title search and live Total / Active / Done counters.
  • Testing & Portfolio Publishing: To verify the API with automated tests and publish the complete source code with a structured README.md and screenshots on GitHub.

4. PROJECT DESCRIPTION

4.1 System Overview and Architecture

TaskFlow is an end-to-end full-stack web application in which a browser client communicates with an Express server over JSON. A user can add a task with a title, priority (Low / Medium / High) and an optional due date, mark it done with a checkbox, delete it, filter the list by status, and search by title. Tasks that are past their due date and not completed are highlighted in red. As structured in the public GitHub repository (FST_AAT1), the project is organised into three cooperating parts:

  1. Frontend Task Interface (public/): index.html, style.css and app.js render the statistics cards (total, active, done), the add-task form, the filter tabs, the search box and the task list. All task titles are escaped before being inserted into the DOM.
  2. Backend API (app.js, server.js): createApp(dataFile) builds the Express application and accepts the storage path as a parameter, so tests can use a temporary file. A validate() helper normalises and checks every request body before it is saved.
  3. Automated Tests (test/api.test.js): Two integration tests exercise the full create → update → filter → delete life-cycle and all invalid-input cases against a live server instance.

5.1 Validation Rules & Statistics Formulation

Every request body is passed through validate() before it is stored. A title is trimmed and must satisfy 1 ≤ length ≤ 120; the priority must belong to the set {low, medium, high}; and a non-empty due date must be parseable by Date.parse. Invalid input returns HTTP 400 with a readable message that the interface shows under the form. For partial updates (PUT) only the supplied fields are validated. The dashboard counters are derived from the stored tasks as:

Active = Total − Done     and     Overdue(t) = (¬t.done) ∧ (t.dueDate < today)

In the demonstration data set of 5 tasks (1 completed), the API returns total = 5, active = 4, done = 1, and the task due on 2026-10-16 is rendered as overdue.

6. IMPORTANT CODE SNIPPETS

The following core snippets from the FST_AAT1 repository illustrate server-side validation, the create-task route, XSS-safe rendering on the client and the automated API test.

6.1 Server-Side Input Validation (app.js)

  const validate = (body, partial = false) => {
    const out = {};
    if (!partial || body.title !== undefined) {
      const title = String(body.title ?? '').trim();
      if (!title) return { error: 'Title is required' };
      if (title.length > 120) return { error: 'Title must be 120 characters or fewer' };
      out.title = title;
    }
    if (body.priority !== undefined) {
      if (!PRIORITIES.includes(body.priority)) return { error: 'Priority must be low, medium or high' };
      out.priority = body.priority;
    }
    if (body.dueDate !== undefined) {
      if (body.dueDate !== '' && Number.isNaN(Date.parse(body.dueDate))) return { error: 'Invalid due date' };
      out.dueDate = body.dueDate;
    }
    if (body.done !== undefined) out.done = Boolean(body.done);
    return { value: out };
  };

6.2 Create-Task REST Route (app.js)

  app.post('/api/tasks', (req, res) => {
    const { error, value } = validate(req.body);
    if (error) return res.status(400).json({ error });
    const tasks = load();
    const task = {
      id: Date.now().toString(36) + Math.random().toString(36).slice(2, 6),
      priority: 'medium',
      dueDate: '',
      done: false,
      createdAt: new Date().toISOString(),
      ...value,
    };
    tasks.unshift(task);
    save(tasks);
    res.status(201).json(task);
  });

6.3 XSS-Safe Rendering (public/app.js)

// Escape user text before inserting into HTML (prevents XSS).
const esc = (s) => s.replace(/[&<>"']/g, (c) => ({ '&': '&amp;', '<': '&lt;', '>': '&gt;', '"': '&quot;', "'": '&#39;' }[c]));

6.4 Integration Test – CRUD Life-Cycle (test/api.test.js)

test('create, list, update, filter and delete a task', async () => {
  let res = await call('/tasks', 'POST', { title: 'Write report', priority: 'high' });
  assert.strictEqual(res.status, 201);
  const task = await res.json();
  assert.strictEqual(task.priority, 'high');
  assert.strictEqual(task.done, false);

  res = await call(`/tasks/${task.id}`, 'PUT', { done: true });
  assert.strictEqual((await res.json()).done, true);

  assert.strictEqual((await (await call('/tasks?status=done')).json()).length, 1);
  assert.strictEqual((await (await call('/tasks?status=active')).json()).length, 0);
  assert.deepStrictEqual(await (await call('/stats')).json(), { total: 1, done: 1, active: 0 });

  assert.strictEqual((await call(`/tasks/${task.id}`, 'DELETE')).status, 204);
  assert.strictEqual((await call(`/tasks/${task.id}`, 'DELETE')).status, 404);

9. CHALLENGES FACED

  • Designing a Testable Backend: A hard-wired storage path would make tests modify real user data. The data file location was therefore passed into createApp(dataFile), allowing the tests to run against a temporary file.
  • Consistent Validation for Create and Partial Update: POST requires a title whereas PUT may send only done. A single validate(body, partial) function with a partial mode was written to serve both routes without duplicated rules.
  • Preventing Cross-Site Scripting: Task titles are user-controlled and were first inserted through innerHTML. An esc() helper that converts & < > " ' was added so that stored text is always displayed as plain text.
  • Test Runner and Repository Hygiene: Node 22 failed to run node --test test/ on a directory, so the script was changed to the explicit test file path. The runtime file data/tasks.json was added to .gitignore so that local task data is never published.
